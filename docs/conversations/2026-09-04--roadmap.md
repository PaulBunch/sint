# Интеграция ROADMAP в критические документы и выбор симулятора

## Summary
Обсуждение роли `ROADMAP.md` в иерархии документации проекта и целесообразности использования симуляторов (MuJoCo, Isaac Sim) для DFAA. Решено добавить ROADMAP в список критических документов в `AGENTS.md` и `long-term-memory.md` как высокоуровневый план фаз. Симуляторы признаны полезными инструментами для валидации кинематики и обучения контроллеров (начиная с Phase 2), при этом MuJoCo рекомендован для начальных этапов из-за точности контактов и простоты. Согласовано включение задач по оценке и настройке симуляции в ROADMAP.

### Почему стоит добавить

ROADMAP — это живой высокоуровневый план фаз и приоритетов. Без него агент легко «теряется» между:
- `spec.md` (что должно быть),
- `current-state.md` (что есть сейчас),
- `handoff-latest.md` (что делать прямо сейчас).

ROADMAP закрывает именно вопрос «в какой фазе мы находимся и что является следующим крупным блоком работы».

### Как интегрировать без дублирования и противоречий

Рекомендуемая иерархия документов (от самого стабильного к самому оперативному):

| Документ                | Роль                                      | Частота обновления      |
| ----------------------- | ----------------------------------------- | ----------------------- |
| `docs/spec.md`          | Цели, ограничения, требования             | Редко                   |
| `docs/ROADMAP.md`       | Фазы, крупные вехи, направление           | При смене фазы / существенном пересмотре |
| `docs/current-state.md` | SSOT — что реально есть сейчас            | После каждого значимого изменения |
| `docs/handoff-latest.md`| Конкретные следующие 3–5 шагов            | В конце каждой сессии   |
| ADR                     | Зафиксированные архитектурные решения     | При принятии решения    |

**Ключевые правила, которые нужно явно прописать:**

1. ROADMAP — это **направляющий** документ, а не жёсткий контракт. Его можно и нужно уточнять (как уже написано в Phase 0).
2. `current-state.md` остаётся единственным источником правды о текущем состоянии железа/софта.
3. `handoff-latest.md` всегда должен указывать на конкретные шаги внутри **текущей** фазы ROADMAP.
4. При завершении фазы или существенном изменении приоритетов:
   - обновляется ROADMAP,
   - факт фиксируется в `current-state.md`,
   - при необходимости создаётся ADR.

### Конкретные правки

**1. В `AGENTS.md` → раздел Critical Documents (read first)**

Добавить строку:

```markdown
- `docs/ROADMAP.md` — High-level phased plan. Read to understand current phase and major priorities. Update when a phase is completed or priorities shift significantly.
```

И слегка расширить Workflow:

```markdown
1. Read `current-state.md` + latest handoff + relevant ADR/spec + current phase of `ROADMAP.md` before making changes
```

**2. В `docs/long-term-memory.md` → Level 3. Hierarchical “Project Bible”**

Добавить:

```markdown
- `docs/ROADMAP.md` — Living high-level plan of phases and key milestones. Refined as experience accumulates. Not a substitute for `current-state.md` or handoff.
```

**3. Размещение файла**

Лучше всего положить как `docs/ROADMAP.md` (рядом с остальными критическими документами).

---

Такой подход сохраняет чистоту разделения ответственности и не создаёт логических противоречий: ROADMAP отвечает на вопрос «куда идём», а не «где мы сейчас» и не «что делать в ближайшие 2 часа».

### Разница между Isaac Sim и MuJoCo (2026)

| Аспект                  | **MuJoCo**                                      | **Isaac Sim ( + Isaac Lab)**                          |
|-------------------------|-------------------------------------------------|-------------------------------------------------------|
| **Разработчик**         | Google DeepMind                                 | NVIDIA                                                |
| **Лицензия**            | Apache 2.0 (полностью открытый)                 | Бесплатный, но проприетарный (Omniverse)              |
| **Физика**              | Очень точная контактная динамика (soft contact), отлична для манипуляций | PhysX 5 + Newton (MJWarp), хорошая, но требует настройки для contact-rich задач |
| **Скорость / параллелизм** | Отличная (особенно MJX на GPU/TPU)             | Лучшая в классе — тысячи параллельных сред на одной RTX |
| **Рендеринг**           | Базовый / средний                               | Фотореалистичный (RTX path-tracing)                   |
| **Сенсоры**             | Ограниченные                                    | Камеры, LiDAR, depth, IMU и т.д. на высоком уровне    |
| **Импорт моделей**      | MJCF / URDF                                     | USD, URDF, MJCF, CAD (Onshape и др.)                  |
| **Главные сильные стороны** | Contact-rich манипуляции, быстрый RL, лёгкий старт | Синтетические данные, digital twin, масштабный RL, ROS 2 |
| **Слабые стороны**      | Слабый визуал, меньше готовых сенсоров          | Тяжёлый (нужна хорошая RTX), крутая кривая обучения   |
| **Когда выбирать**      | Точная физика сборки, обучение политик, быстрые итерации | Визуальное обучение VLA, sim-to-real с камерами, большие параллельные эксперименты |

**Кратко**:  
- **MuJoCo** — «золотой стандарт» для точной физики контактов и быстрого обучения контроллеров/политик.  
- **Isaac Sim** — когда нужны реалистичные камеры, масштаб и digital twin.

### Насколько это подходит для sint (DFAA-сценарий)

DFAA — это в первую очередь **физическая** самосборка с реальными допусками, акустикой, тактильной обратной связью и 100% COTS-деталями. Полностью заменить реальное железо симулятором нельзя (особенно по акустике, люфтам 3D-печати, тепловым эффектам и «ощущению» реальных соединений).

Однако симуляторы очень полезны на определённых этапах:

**Полезные сценарии для sint**:
1. **Быстрая проверка кинематики и коллизий** (до изготовления первого железа).
2. **Тестирование алгоритмов планирования движений** и стратегий сборки.
3. **Обучение / тонкая настройка low-level контроллеров** (сила, импеданс, последовательности стыковки).
4. **Генерация синтетических данных** для VLA-агента (особенно с камерами) — здесь Isaac Sim сильно выигрывает.
5. **Отработка сценариев самосборки** (стыковка доков, смена EE, перебазирование) в безопасной среде.
6. **Сравнение вариантов кинематики** (6 vs 7 DoF, симметричная схема) без траты денег на прототипы.

**Ограничения**:
- Акустическая прозрачность почти не моделируется.
- Реальные люфты, упругость 3D-печатных деталей и «хруст» защёлок симулируются плохо.
- Thermal behavior и реальная потребляемая мощность — слабо.
- Полный DFAA-цикл (агент сам печатает/собирает улучшенную версию) в симуляции возможен только частично.

### Стоит ли добавлять в ROADMAP?

**Да, но не как обязательный критический пункт ранних фаз**, а как опциональный/рекомендуемый инструмент начиная с Phase 2–3.

Рекомендую добавить так:

В **Phase 1 (Foundation)** — только исследование:
- [ ] Evaluate simulation tools (MuJoCo / Isaac Sim / alternatives) for kinematics validation and early controller testing

В **Phase 2 или 3** — практическое использование:
- [ ] Set up simulation environment (prefer MuJoCo for contact-rich assembly, Isaac Sim if photorealistic vision data is needed)
- [ ] Validate kinematic scheme and basic assembly sequences in simulation before physical prototype
- [ ] Use simulation for controller tuning and synthetic data generation for VLA agent

В **Refinement Notes**:
- [ ] Assess sim-to-real gap after first physical joint module tests
- [ ] Decide whether to invest in Isaac Sim digital twin once multi-DoF node exists

### Практическая рекомендация для sint

На старте (пока нет железа) — **MuJoCo** значительно предпочтительнее:
- Легко ставится (`pip install mujoco`)
- Отличная точность контактов (именно то, что нужно для сборки)
- Хорошо работает с LLM-агентами (много готовых обвязок)
- Не требует мощной RTX

Isaac Sim имеет смысл подключать позже, когда:
- появятся реальные CAD-модели,
- понадобятся качественные синтетические изображения для обучения vision-части VLA,
- или когда захочется делать полноценный digital twin.

**Итог**: добавлять стоит, но как вспомогательный инструмент валидации и ускорения разработки, а не как замену физическому прототипированию. DFAA в итоге всё равно проверяется на железе.
